# ADR 001: How we stop double bookings

Status: accepted, 2026-11-10. Amended the same day after the design review (isolation set explicitly, `SET LOCAL` timeouts, the hash check inside the loop, vehicle ownership moved to code).

## The problem

A booking needs a free bay and a free qualified technician for the whole service duration (and the vehicle can't be in two places at once). Two customers can ask for overlapping times at the same dealership at the same moment, from two different API instances. The classic race: both read "bay 1 is free", both insert, and two cars turn up for one bay.

There are two rules to hold, and the second one is easy to forget:

- **Safety:** no two active appointments overlap on the same bay, the same technician or the same vehicle.
- **No false "fully booked":** a 409 must mean nothing is free. Losing a race to another request is never a reason to turn a customer away while another bay and technician are still free (A19 in ASSUMPTIONS.md).

## Options I looked at

I had a Fable agent compare the options and run the claims that matter against Postgres 16. My own reproduction of the deadlock claim is in [docs/evidence/deadlock-repro.sh](../evidence/deadlock-repro.sh). The short version:

| Option                                                                               | Why not (or why)                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Postgres exclusion constraints, plain `INSERT`, retry on 23P01                       | This was my first idea. It is safe, but when inserts for the same bay land at the same instant each one waits for the other and Postgres kills one with a deadlock (40P01) after 1 second. I reproduced it myself: 16 clients for 10 seconds gave 1 commit, 11 failures and 26 deadlocks. Under a burst that turns into false refusals and very slow requests. |
| **Exclusion constraints, `INSERT ... ON CONFLICT DO NOTHING`, re-read on zero rows** | **Chosen.** Same guarantee. Postgres inserts "speculatively", so when two inserts meet, one backs off instead of both waiting. Same test: 8,819 commits, 0 failures, 0 deadlocks. A conflict returns zero rows and doesn't abort the transaction.                                                                                                              |
| `SELECT ... FOR UPDATE` on bay and technician rows                                   | Works, but only at READ COMMITTED and only if the lock and the read are two separate statements. The agent showed two natural-looking ways to write it (one combined statement, or REPEATABLE READ) that double booked with no error. The rule also lives only in the code, so a future reschedule endpoint or a hand-written fix can skip it.                 |
| SERIALIZABLE with retry on 40001                                                     | Simplest code, but it aborts bookings that don't even overlap, because Postgres tracks reads per index page. On a small table (every new install and every test database) 61% of transactions retried at 32 clients. And one writer that forgets the isolation level double books silently.                                                                    |
| Advisory lock per dealership                                                         | Easiest to explain ("one booking at a time per dealership"). But it is again a convention that every writer has to follow, it queues every booking at a dealership behind the slowest one, and it also double booked at REPEATABLE READ.                                                                                                                       |
| Redis lock                                                                           | Two systems that nothing ties together. A slow holder can lose the lock to its TTL and still insert, and a failover can forget a lock. Without a database constraint behind it, it can double book. With one, it only adds a service to run. All the data already lives in one Postgres, so there's nothing for Redis to coordinate.                           |

## The decision

1. **The database is the guarantee.** Three exclusion constraints on `appointments` (bay, technician, vehicle), each `(resource_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)`, built from the two timestamp columns so no row can carry other bounds, for every row that isn't cancelled (`status <> 'cancelled'`). Using "not cancelled" instead of "confirmed" means any status we add later (say `in_progress`) holds its bay by default, which is the safer mistake. These hold for every writer at every isolation level: the API, a script, a future reschedule endpoint, somebody in psql.
2. **The booking write is `INSERT ... ON CONFLICT DO NOTHING RETURNING`.** The availability read uses exactly the same range expression and the same status filter as the constraints. If the read were stricter it would say "no slot" while a pair is free, and if it were looser the loop would keep offering a bay the constraint keeps refusing. A test on generated data checks that the two agree.
3. **The idempotency key goes first.** If the request has an `Idempotency-Key`, the very first thing is to look it up for that customer, before any other check. Same request: replay the original appointment (even if its start time has passed by now, because the customer is asking "what happened to my booking", not booking again). Different request: 422. Only then do the normal checks (404s, opening hours, time window) run.
4. **The loop, at READ COMMITTED, with each attempt as its own short transaction.** The service sets the isolation level on every transaction itself instead of trusting the database default, because at REPEATABLE READ `ON CONFLICT DO NOTHING` raises 40001 instead of returning zero rows, and every lost race would turn into a 503. Every attempt starts with one read that answers, in this fixed order:
   - is this idempotency key already booked? (again, because a twin request with the same key may have just committed) - compare the request hash exactly as at the start: same request, replay it, different request, 422 `IDEMPOTENCY_KEY_REUSED`. A twin with a different body must never get back somebody else's booking.
   - is the vehicle already booked at an overlapping time, at any dealership? - 409 `VEHICLE_ALREADY_BOOKED`
   - did the customer ask for a technician who is now busy? - 409 `TECHNICIAN_UNAVAILABLE`
   - is there no free bay, or no free qualified technician? - 409 `SLOT_UNAVAILABLE`. **Only this fresh read is allowed to say "no slot", never a counter running out.**
   - otherwise insert the first free pair. One row back means booked. Zero rows means somebody got in first, so go round again, and the next read works out what changed. The order matters: a replayed request would otherwise see "its own" vehicle as busy and get a 409 for a booking it actually has.

   That's the order of the answers, not of the SQL. Found while building: at READ COMMITTED every statement in the transaction gets its own snapshot, so a later statement can see rows an earlier one missed. The read therefore runs the free bay and technician lists first, then the vehicle and preferred technician checks, and the key lookup last. A twin that commits halfway through can then only make a later check stricter. If the key lookup ran first and missed a twin that the vehicle check then saw, the twin would get a false `VEHICLE_ALREADY_BOOKED`. A comment in `readSlot` says the same, because no test can catch the order being swapped (the race barrier holds requests before the read, not between its statements).

5. **The bound.** Every lost race proves a competitor committed a booking on that bay or technician, so the next read won't offer it again. With B free bays and T free technicians at the first read, a request can lose at most B + T - 1 races before it either books or gets an honest 409 (without cancellations, which don't exist yet). The agent saw at most 10 attempts for a booking and 11 for a "no slot" with 10 bays and 10 technicians. The read returns the ordered lists of free bays and free qualified technicians (not just the first of each), so the hard cap can be taken from that first read: B + T + 2 lost races, where T is 1 when the customer asked for a technician (only that one can be used). Only lost races use up the cap, a database error has its own budget (decision 6). On top of that, a time budget: no new attempt starts once 5 s are gone. Hitting either one means something odd is going on, so the answer is **503 with Retry-After**, not 409. A fixed small cap would hand out false 503s at a big dealership during a burst.
6. **Errors that prove nothing** (deadlock 40P01, serialization failure 40001, lock timeout 55P03) get a separate small budget of 3 retries per request (so 4 tries in all) and then 503. They say nothing about free slots, so they never count towards a 409. With `ON CONFLICT DO NOTHING` at READ COMMITTED none of them showed up in the tests, so this is a backstop. A statement timeout (57014) is a sign of overload, so it goes straight to 503 without a retry.
7. **Timeouts on every booking transaction**, set with `SET LOCAL` so they end with the transaction and still work behind PgBouncer in transaction mode (a session-level `SET` would stick to whichever server connection ran it): `lock_timeout` 2 s and `statement_timeout` 5 s by default. The 5 s loop budget is checked before each attempt, so it means "no new attempt after 5 s", not a hard ceiling. An attempt already running finishes or hits its own timeouts, and getting a pool connection has its own 2 s timeout, so the worst case is still bounded. 2 s is far above the normal wait behind a competitor's commit (150 ms worst case in the agent's burst test), so the ordinary wait never turns into a false 503.
8. **No lock in front.** The loop is the main path and runs all the time under load, so it stays tested. If the retry metric ever shows real pain, an advisory lock per dealership and local day in front of the same loop is the lever (the constraint stays the guarantee).

## What the constraint does not cover, and how each gap is closed

| Gap                                                                           | Closed by                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bay or technician from another dealership                                     | Composite foreign keys `(dealership_id, service_bay_id)` and `(dealership_id, technician_id)`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Vehicle not owned by the customer                                             | **Checked by the service at booking time, not in the schema.** I first had a composite foreign key `(customer_id, vehicle_id)`. The design review pointed out that cars get sold: with that key, an old appointment would block changing the vehicle's owner. Ownership at booking time is a point-in-time fact, like the skill, so it lives in code with a test. Facts that must never change (which dealership a bay or technician belongs to) stay in the schema.                                                                                                                                                                                                                                                |
| Empty range (start = end overlaps nothing, so it slips past every constraint) | `CHECK (ends_at > starts_at)`, `NOT NULL` on every id and time                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Technician lacks the skill                                                    | **Checked in the candidate query, not in the schema.** A composite foreign key to `technician_skills` would work (the agent tested it), but then a skill could never be removed from a technician who has ever had an appointment using it, past ones included. I'd rather keep that check in code, with tests, than make the skill list impossible to edit. A small race remains (a skill removed in the milliseconds between read and insert), which I accept. With a preferred technician the window is wider: their skill is checked once before the loop, not again in each attempt, so a skill removed during a long loop could still be booked once. Same kind of race, and I accept it for the same reason. |
| Opening hours, time zone, the 15 minute grid, booking window                  | Pure scheduling code with unit tests, before any query                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

## Trade-offs I accept

- Under a burst for the exact same slot, requests walk down the list of bays and technicians (the agent measured 4.5 attempts on average with 32 clients all asking for one slot, 10 at most). That's because the pick is deterministic (A16). I'd rather keep the pick easy to reason about and test. Spreading requests across bays is a tuning step if the metric says so.
- `ON CONFLICT DO NOTHING` doesn't say which constraint got in the way, and with no conflict target it also swallows a clash on the idempotency key. The next attempt's read works it out, and it needs that read anyway.
- Exclusion constraints aren't supported on partitioned tables in Postgres 16. I checked Postgres 17 too: it allows them only when the partition key is part of the constraint with equality. The vehicle constraint deliberately has no dealership in it (a car can't be in two places), so partitioning by dealership is off the table on any version without giving up that guarantee. At the volume in A23 (my estimate) one table is fine for years, and old rows can be archived out instead.
- `btree_gist` has to be available. It ships with Postgres, it's a trusted extension, and the managed Postgres services I know of offer it.
