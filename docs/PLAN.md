## Notes for the steps

- Step 1: AC-16's "exactly 90 × 24 hours" case uses its own clock (`2027-03-02T09:00:00Z`, given in the spec), because 90 days after the shared "now" lands on a Sunday when North is closed. The AC-14 end time tests also need their own instants, since October is past the window from the shared clock.
- Step 2: red is the first migration with all the tables but no constraints, checks or unique index. The AC-21 inserts then succeed and the assertions fail on that, not on a missing table. The constraints, checks and the `(customer_id, idempotency_key)` unique index go in during green. That's also the honest proof that each constraint is what refuses the row. The idempotency columns are part of this migration, even though the code that uses them comes in step 8.
- Step 2: each integration test file gets its own database cloned from a migrated template, so files can run in parallel and never see each other's rows.
- Step 4: the tests assert domain results (the created appointment, or the error code), not HTTP status codes. The status mapping is step 5's job.
- Step 4: the concurrency tests (AC-23, AC-24, AC-39, AC-40, and AC-38 with the database default set to REPEATABLE READ) are written in the red half, against the service, before the loop exists. Red here means a single attempt with no re-read, which should fail AC-24 on the count of created rows. They need a database pool of at least 25, or the pool queues the requests and the race never happens, and a generous time budget so a slow machine doesn't give a 503.
- Step 4: `lock_timeout` (default 2 s), `statement_timeout` (default 5 s) and the loop time budget (default 5 s) come from config. The timeouts are set with `SET LOCAL` inside each booking transaction, so they work behind PgBouncer in transaction mode.
- Step 4: the idempotency hook (the key lookup at the start of each attempt) arrives in step 8. Step 4 leaves the loop shaped so it slots in at the top without moving anything else.
- Step 5: the table-driven e2e test sends one request per domain error and checks its status and `code` (`SLOT_UNAVAILABLE` 409, `TECHNICIAN_UNAVAILABLE` 409, `VEHICLE_ALREADY_BOOKED` 409, `OUTSIDE_OPENING_HOURS` 422 and so on, `BOOKING_CONTENDED` 503 with `Retry-After`), plus AC-01 end to end with the full response body.
- Step 6: the two teeth checks, each run once and logged in `docs/evidence/teeth-checks.md`. With the exclusion constraints dropped, AC-23 must double book. With the re-read removed (zero rows returns 409 straight away), AC-24 must create fewer than 3. The first shows the safety half of ADR 001, the second the "no false 409" half.
